# C#の処理時間と精密数値の改善

2026-10-12、Linux・.NET SDK 10.0.401で測定しました。CI分割とは独立した変更です。

`Number` は整数・ゼロの構築で不要な最大公約数計算を省き、既に互いに素な分数では除算を省きます。分母が等しい比較では分子だけを比較します。任意精度の分数、符号の正規化、ゼロ除算拒否、PICへの丸め規則を保持します。

変更前 `1184d59` の `Number.cs` と変更後の実装を別namespaceへ読み込み、同じReleaseプロセスで交互に測定しました。各500万回、事前にwarmupし、11回の中央値を使用しています。全反復で結果の分子・分母の一致も確認しました。

| 加算の対象 | 変更前 | 変更後 | 結果 |
|---|---:|---:|---|
| 整数1の繰り返し | 311.197ms | 52.285ms | 5000000 / 1 |
| 小数0.01の繰り返し | 226.204ms | 218.531ms | 50000 / 1 |
| 分数1/3の繰り返し | 199.367ms | 152.118ms | 5000000 / 3 |

整数加算のこの測定は約6倍ですが、実際の業務処理やCI全体の倍率を表すものではありません。小数の差は小さく、機械負荷やJITで変動します。巨大整数を含む加減算・比較・約分と負の分母、ゼロ、long.MinValueをRuntime回帰で検証します。

固定carddemo lock `cfac36e479280b2e657d0ce646affc064ef12b635ea78803c7874828ce110168` の3ケースを `evaluate --build --shard-index 0 --shard-count 16` で測定しました。代表ケース `carddemo-f966744c7135` は解析591ms、strict拒否614ms、scaffold生成24933ms、生成後build1658msでした。scaffold生成には探索用ビルドと200候補の別プロセス試行が含まれます。3ケース中1件は生成拒否、2件は生成・ビルド成功であり、部分評価をコーパス全体の成功として扱いません。

同ケースを直接APIでも測定し、初回を除く5回の中央値は解析 `FrontendAnalyzer.Analyze` が314.151ms、コード生成 `SourceBackend.Generate` が146.272ms（2156656文字）でした。この生成測定はレポート初期化、ディスクへの書き込み、分岐探索とSDKビルドを含みません。探索工程の改善余地が大きく、試行ごとのプロセス起動費用を減らす検討には、状態の分離・タイムアウト・異常終了後の復旧を保つ必要があります。

測定の数値と入力識別子は [number.json](../tests/runtime-performance/number.json) に保存し、公開原文は含めません。

後続の探索プロセス起動削減は [probe-performance.md](probe-performance.md) に独立した測定として記録しています。
